# Sales Receipt workspace

The Receivables workspace now exposes a Sales receipts tab. Its company/period-scoped list reads saved receipts in pages of 25 with previous, next and refresh actions. Receipt numbers open persisted detail; the Open journal action uses the existing journal client and lineage drill, gated by GL.JE.VIEW. Makers with AR.SALES_RECEIPT.CREATE and ATTACHMENT.CREATE can create a receipt in an open period without receiving AR.VIEW merely to open the form.

Company, period, API and actor changes remount the read workspace. AR.VIEW and an unexpired current access snapshot are required to expose list controls. The server reauthorizes every read. Requests carry bearer authorization and no-store semantics; amounts remain decimal strings through validation and display.

A selected row is checked against a fresh detail response before opening. Changed status/revision/period/journal revision requests a list refresh. The journal client checks actual journal revision, currency and state before opening the drill. Failed refreshes clear old rows. Async completions after unmount do not update the old company view. Returning from detail focuses the rebuilt row button; returning from the journal focuses its launch button.

The actual Receivables React component with simulated APIs passed 15 browser checks at 1280px and 390px, including pagination, final-page bounds, exact amount presentation, detail and journal reads, focus restoration, stale-record rejection, error recovery and absence of full-page horizontal overflow. This is isolated browser evidence, not deployed API or identity-provider acceptance. A narrow screenshot was visually inspected. Client and SSR coverage validates response and access boundaries. Full local suite results and exact-candidate CI must be recorded before publication.

The native form searches eligible customer, bank, cash account and category masters, accepts an exact amount and description, verifies supporting evidence through the attachment workflow and sends a scoped Draft command. Preparation rechecks actor/access and open period; the server revalidates all masters. Confirmed creation exposes the actual journal through the existing Draft workflow callback and refreshes the receipt list on close.

The original body, key, chosen masters and verified attachment are retained before sending, scoped by API/company/period/actor. Returning after navigation restores pending input and allows same-request replay after a period closes; fresh closed-period entry stays unavailable. Replay rechecks original identity and access without repeating period preparation. Attempts are counted so a late rejection from an older request cannot erase recovery after another attempt started. Confirmed success clears recovery even after unmount. This recovery exists in the current page session only; reloading or restarting the browser is not durable request recovery. Upload recovery before command preparation is also outside this increment.

The actual entry component with simulated APIs passed 16 browser checks at both widths: four master selections, verified attachment reservation, exact amount, held POST/remount, closed-period resume, access denial before POST, original body/key replay, no repeated attachment upload, actual Draft callback, list refresh and focus, and clearing recovery after confirmation. Narrow form and list screenshots were visually inspected. These mock-backed browser runs do not establish live accounting acceptance.

Bank matching, cancellation/refund, multi-category/tax entry, durable reload recovery, independent audit and live business acceptance remain incomplete. No real accounting write or live permission change is part of this increment.

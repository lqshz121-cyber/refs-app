# Context issuance during grant changes

A real PostgreSQL 16 read/write dependency cycle reproduced a failed context issuance. The issuer transaction read its actor's grants and inserted an uncommitted capability; a concurrent serializable grant refresh read the context population and updated the grant, then committed first. Issuance failed with SQLSTATE 40001 after one attempt. No capability or audit row from the failed transaction survived. This reproduction did not inject an artificial database error.

Issuance now uses the existing bounded serializable transaction retry helper, matching the accounting runtime's transaction policy. The authenticated principal and random token/hash are chosen once outside the retry. Each attempt re-executes the complete database issuance function, including current-grant validation, and either commits the capability and audit together or rolls both back. Authorization failures are not retried. Revocation and cleanup implementations, runtime timeouts and database policy remain unchanged.

Unit tests cover statement/commit failures, read/write issuance, stable identity, bounded attempts, connection release and authorization denials. Fresh PostgreSQL 15 and 16 each passed all three selected scenarios without skips: concurrent grant refresh, concurrent revocation and the authenticated attachment HTTP lifecycle. The refresh committed exactly one additional capability and audit after two attempts; revocation returned 42501 after two attempts with no retained capability or audit. Root and server test commands also passed. Full regression validation remains pending. The separately observed attachment reservation 503 still requires full-suite confirmation; this reproducible issuance defect is not presented as proof that every attachment failure has the same cause.
